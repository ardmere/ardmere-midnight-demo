## Slide 3 — Industry pain

**Kicker**: 01 · INDUSTRY PAIN

**Title**: Proof of reserves is still a specialist build.

**Subtitle**: Fragmented proofs, high cryptography cost, and verification that is too hard for users.

**Three cards**

1. **Fragmentation**

   Every exchange builds its own proof system, circuit, tree and verifier. Regulators, users and independent third parties have no common verification tool, so snapshots cannot be compared across exchanges.
2. **Cost and scarce expertise**

   ZK circuits require specialist engineers and continuous security review; smaller operators cannot justify a bespoke build.
3. **Verification is too hard**

   Users are asked to verify global proofs themselves and follow long exchange runbooks — so most users never verify.

**Speaker notes**: The assessment document highlights fragmentation and cryptographic cost; the third pain is the user-facing verification burden.

## Slide 4 — Who needs this

**Kicker**: 01 · WHO NEEDS THIS

**Title**: Who needs a standard PoR protocol?

**Subtitle**: The buyer is the exchange; the beneficiary is the user; the standard is the public good.

**Four audiences**

| Audience                                           | What they need                                                                                                 |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **Mid-tier exchanges**                             | No in-house ZK team. Need a turnkey way to build, prove and publish a snapshot.                                |
| **Regulators, auditors and independent verifiers** | One schema and one verifier, so snapshots from different operators are comparable and independently checkable. |
| **Users**                                          | A simple inclusion check against the anchored root — no global proof, no long runbook.                         |
| **Custodians / payment institutions**              | The same reserve-attestation pattern beyond centralized exchanges.                                             |

**Bottom line**: Lower cost for operators, comparability for regulators and independent verifiers, and a one-path check for users.

**Speaker notes**: This is the demand side. The standard is a public good, but the exchange is the buyer because it reduces compliance and engineering cost. Regulators, auditors and independent verifiers get the same schema and the same check, which is what makes cross-exchange comparison possible.

## Slide 5 — Why Midnight

**Kicker**: 02 · WHY MIDNIGHT

**Title**: Midnight makes PoR a protocol, not a project.

**Subtitle**: Private witness, public verification, and automatic proof checking at submission.

**Four cards**

1. **Compact**

   TypeScript-like ZK contracts with explicit `disclose()`; the circuit and verifier are generated by the compiler.
2. **Private state**

   Balances and `userIdHash` values stay in the witness; they never reach the public ledger.
3. **Public ledger**

   Only the anchored root, prices, reserves and aggregate values are stored.
4. **Automatic verification**

   When the exchange submits, the contract verifies the global proof. An invalid proof cannot update state.

**Bottom line**: The global proof is a submission-time check, not a user task.

**Speaker notes**: This is the key UX shift. Midnight's dual-state model and on-chain verification make the protocol practical: the operator proves once, the contract verifies once, and users only check their own path.

## Slide 6 — Hard problems and responses

**Kicker**: 03 · SOLUTION

**Title**: Four hard problems. Four design responses.

**Four cards**

1. **Scale**

   Bounded batch proofs today; sharded batches and aggregation for large user bases.
2. **Cross-chain reserves**

   A `reserveProofHash` anchor plus challenge-response and block-height/time locking for external assets.
3. **Omission attacks**

   A standardized inclusion path and a one-path local verifier/skill, so users can confirm they were not left out.
4. **Compiler and cryptography trust**

   Pin an audited Compact version and state the compiler / proof-system trust boundary explicitly.

**Speaker notes**: These are the four bottlenecks from the assessment: scale, cross-chain asset anchoring, omission, and compiler trust. The next slides show how the protocol addresses them.

## Slide 7 — Architecture

**Kicker**: 03 · SOLUTION

**Title**: Exchange-local proving, chain-level verification.

**Subtitle**: The exchange keeps the data; Midnight keeps the commitment.

**Diagram roles**

- **Exchange local**
Builds the MST, runs the proof server, keeps private balances, emits inclusion JSON.
- **Midnight contract**
Verifies the global proof at submission, anchors the root and public fields, enforces authority.
- **User**
Reads the anchored root and verifies one Merkle path locally with a simple skill.
- **Regulator / auditor**
Reads the same public state and snapshot history; compares operators on one schema.

**Speaker notes**: The division of labor is deliberate. The exchange does the heavy proving; the contract does the global verification; the user does only a local path check.

## Slide 8 — Snapshot schema

**Kicker**: 03 · SOLUTION

**Title**: One snapshot schema for every exchange.

**Subtitle**: Same fields, same encoding, same verifier.

**Table**

| Field | Purpose |
| --- | --- |
| `snapshotId`, `timestamp` | Ordered snapshot identity and time anchor |
| `merkleSumRoot` | The root users check their inclusion path against |
| `declaredReserves` | Per-asset reserves, as a vector or a commitment |
| `declaredLiabilities` | The aggregate liabilities proved by the circuit |
| `reserveProofHash` | External-chain reserve anchor (production extension) |
| `authority`, `published` | Who may publish; whether the snapshot is live |

**Note**: The reference implementation covers the root, prices, reserves, aggregate sums, authority and published flag. `reserveProofHash` is the extension point for cross-chain reserves.

**Speaker notes**: Standardization is mostly about agreeing on fields and encoding. Once the schema is fixed, the same verifier works for every operator.

## Slide 9 — Circuit guarantees

**Kicker**: 03 · SOLUTION

**Title**: What the circuit actually guarantees.

**Six checks**

1. **Authority** — only the operator's coin public key can publish.
2. **Balance encoding** — non-negative in the assessment MVP; canonical signed `(pos, neg)` in the reference implementation. This is a representation check, not a solvency check.
3. **Per-user solvency** — net asset value > 0 at the submitted public prices. A single-asset net balance may be negative; the weighted sum across assets must be positive.
4. **Root integrity** — the recomputed MST root equals the anchored root.
5. **Reserve check** — total or per-asset exposure is within declared reserves.
6. **One-shot publication** — `published` prevents silent replacement.

**Speaker notes**: Balance encoding is not the solvency check. Because the reference supports lending and short positions, a single-asset net balance may be negative; solvency is enforced by per-user NAV > 0 at the submitted prices. In a single-asset deployment this reduces to net balance > 0. The assessment MVP uses non-negative balances and total liabilities ≤ reserves; the reference generalizes the same integrity pattern to signed multi-asset balances, per-user NAV and per-asset exposure.

## Slide 12 — User verification

**Kicker**: 04 · DEMO — USER VERIFICATION

**Title**: Verification in one Merkle path.

**Subtitle**: The global proof is verified once, by the contract. The user verifies only their own inclusion path.

**Three steps**

1. **The contract anchors the root**

   At submission, the contract verifies the global proof and stores the root only if the proof is valid.
2. **The user receives an inclusion JSON**

   The file contains sibling nodes, the user's signed balances and the published prices.
3. **One local check**

   Recompute the leaf and the parent steps; compare the result with the anchored root. Optionally check NAV > 0.

**UX mock**

```text
$ verify-user --root 0x115b… --path alice.json
✓ leaf included
✓ root matches
✓ NAV > 0
```

**Bottom line**: No proof server. No global proof. No exchange runbook. No public balance disclosure.

**Implementation note**: The reference CLI is `npm run verify-inclusion`; the production form is a one-click verification skill or browser widget.

**Speaker notes**: This is the UX differentiator. Existing PoR flows ask users to verify the global proof and follow complex instructions. Here the global proof is already checked by the contract; the user only checks one path, which a simple skill can automate.

## Slide 13 — Trust boundary

**Kicker**: 04 · DEMO / TRUST

**Title**: What this proves — and what it does not.

**Proved by the circuit**

- MST root consistency
- Canonical signed-balance encoding
- Per-user NAV > 0 at the submitted prices
- Exposure within declared reserves
- Only the authority can publish

**Not proved**

- Prices reflect the real market
- Reserves match real assets
- The batch covers every user
- `userIdHash` maps to a real customer
- The exchange's internal ledger is honest

**Bottom line**: The contract verifies the proof, not external truth. Prices and reserves are operator inputs, not an oracle.

**Speaker notes**: The trust boundary is part of the product. The protocol makes verification cheap; it does not replace external reserve attestation or price oracles.

## Slide 14 — Next

**Kicker**: 05 · NEXT

**Title**: From reference MVP to production PoR.

**Four workstreams**

1. **One-click verification skill**

   A browser widget or CLI that takes the anchored root and an inclusion JSON and returns pass/fail, with no runbook.
2. **Sharded aggregation**

   Bounded batches and a batch-root aggregation tree for large user bases, without changing the user experience.
3. **Cross-chain reserve anchor**

   `reserveProofHash`, challenge-response and time locking so external reserves and liabilities share one timestamp.
4. **Auditor portal and Preprod**

   Snapshot history, schema versioning, compiler audit and the ledger-9 upgrade.

**Closing line**: Verifiable reserves without surveillance.

**Footer**: `github.com/ardmere/ardmere-midnight-demo · Apache-2.0`

**Speaker notes**: Close on the standard and the simple user path. The next milestone is the one-click skill; the larger architecture work is aggregation, cross-chain anchoring and the auditor portal.
